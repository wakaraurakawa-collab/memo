# タイムスタンプ日記 要件定義書

- バージョン: v1.0
- 作成日: 2026-08-14
- ステータス: 合意待ち(実装前レビュー用)

---

## 1. 背景と課題

Windows のメモ帳で `F5` を押すと、カーソル位置に日時が挿入される。この体験が優れているのは次の3点による。

1. **ワンアクション** — キー1回。メニューを開く必要がない
2. **カーソル位置に入る** — 末尾追記ではなく、いま書いている場所にそのまま入る
3. **思考を中断しない** — 手が文章から離れない

一方、iPhone のメモアプリにはこれに相当する機能がない。日付を入れたければ手で打つか、ユーザー辞書に固定文字列を登録するしかなく、**現在時刻・秒までは入れられない**。

結果として「思いついたことを、それを思いついた時刻とともに残す」という行為に摩擦が生まれている。本プロダクトはこの摩擦をゼロにする。

## 2. コンセプト

> **書くことと、時刻を刻むことの間の摩擦がゼロの日記。**

打刻は「機能」ではなく「呼吸」でなければならない。打刻のために指の位置を大きく動かす、画面を切り替える、キーボードを閉じる — これらが1つでも発生した設計は不合格とする。

## 3. 主要な利用シーン

| # | シーン | 求められること |
|---|--------|----------------|
| A | 通勤電車で片手で思いつきを書き殴る | 片手の親指が届く範囲で完結する |
| B | 打ち合わせ中に発言を時刻付きでメモする | 打刻が速い。連続して打てる |
| C | 作業ログを取る(何時に何を始めて何時に終えたか) | 経過時間が後から分かる |
| D | 夜、一日を振り返って追記する | その日のページをすぐ開ける。時系列が読みやすい |
| E | 数ヶ月後に「あの件いつだっけ」と探す | 全文検索と日付ジャンプ |

## 4. 前提(決定事項)

ヒアリングにより以下を確定した。本文書の全設計はこれを前提とする。

| 項目 | 決定 | 理由 |
|------|------|------|
| 主要端末 | **スマートフォン(iPhone / Safari)中心** | iPhone メモの代替が動機。PC でも問題なく使えるようにはするが、UI の最適化はスマホを優先する |
| 記述単位 | **1日1ページへの追記型** | メモ帳 F5 の使い方に最も近い。日記としても自然 |
| 打刻手段 | **画面上のボタンを主役に、複数の手段を併用** | 物理キーがないため。詳細は §6 |
| 保存先 | **ブラウザ内のみ(端末ローカル)** | サーバー不要・ログイン不要・完全プライベート・即公開可能。同期は将来検討 |

### 4.1 この前提から導かれる重要な帰結

- **サーバーを持たない** ため、静的ファイルのみで完結する。GitHub Pages にそのまま置ける。
- **ログイン機構を作らない** ため、初回アクセスから0秒で書き始められる。
- **端末間で同期しない**。これは既知の割り切りであり、代償としてエクスポート機能を必須とする(§6.5)。
- **データ消失リスクは利用者の端末に閉じる**。ブラウザのデータ削除で消えるため、バックアップ導線を UI 上で明示する必要がある。

## 5. スコープ

### 5.1 MVP(第1弾・これが揃って初めてリリース)

- 今日のページを開いて書ける
- 打刻できる(ボタン / 自動 / テキスト展開)
- 自動保存される
- 過去の日付を開ける
- 全文検索できる
- エクスポートできる

### 5.2 Phase 2(MVP が手に馴染んでから)

- タイムラインビュー(その日の打刻を時系列で可視化)
- 経過時間の表示
- 打刻書式のカスタマイズ UI
- ホーム画面へのインストール(PWA)/ オフライン動作

### 5.3 将来検討

- ファイル書き出しによる擬似同期(Dropbox 等に置く運用)
- サーバー同期・複数端末対応
- タグ / 気分記録 / 添付画像

### 5.4 スコープ外(作らないと明言する)

- リッチテキスト編集(太字・色など)。カーソル制御が複雑化し、打刻の速度を損なうため**プレーンテキストに限定**する
- 他人との共有・公開機能
- アカウント登録、課金

## 6. 機能要件

### 6.1 エディタ【MVP・最重要】

- 画面の大半を占める単一のプレーンテキスト入力領域とする
- 1日 = 1つのテキストとして扱う。段落や打刻はすべてこのテキストの中にある
- 開いた瞬間に**今日のページ**が表示され、そのまま書き始められる
- iOS の自動大文字化・自動修正は既定でオフ(設定で変更可)

**設計判断:本文テキストが唯一の正データ(single source of truth)とする。**
打刻の記録を本文とは別のデータ構造に持つと、利用者が本文を編集した瞬間に両者がずれる。したがって打刻情報は本文中に文字列として存在するのみとし、タイムラインなどの派生表示は**本文を解析して生成**する。この方針から、打刻書式は機械的に解析可能な形式でなければならないという制約が生まれる(§6.2.2)。

### 6.2 打刻【MVP・中核】

物理キーボードがないため、単一の手段ではなく**4つの手段を用途で使い分ける**。

#### 6.2.1 打刻の4手段

| 手段 | 操作 | 主な用途 |
|------|------|----------|
| ① 打刻バー | キーボード直上に固定されたボタンをタップ | 通常の打刻。**主役** |
| ② テキスト展開 | 本文に `いま` `きょう` などと打つと即座に日時へ置換 | 文章を書く流れの中で自然に入れたいとき |
| ③ 自動打刻 | 空行を挟んで新しい段落を始めると行頭に自動挿入 | 作業ログ、連続した実況メモ |
| ④ キーボードショートカット | `F5` および代替キー | PC で書くとき |

##### ① 打刻バー(最重要 UI)

- ソフトウェアキーボードの**すぐ上**に固定表示する。指の移動距離を最小にするため、画面上部や別画面には絶対に置かない
- タップしても**キーボードが閉じない・カーソル位置が失われない**こと(§9.2 に技術要件)
- **打刻ボタンは、押し方によらず必ず既定書式で打刻する。** 当初は長押しに書式メニューを割り当てていたが、スマートフォンでは指を置く時間が容易に長押しの閾値を越え、押したのに打刻されない事故が起きた。**主要な操作に、押し方で結果が変わる仕掛けを持たせない**ことを要件とする
- ほかの書式で打刻したいときは、打刻バーの専用ボタンから選ぶ

##### ② テキスト展開

利用者が理想として挙げた「`きょう` と打つと日時が入る」を実現する。iOS のユーザー辞書と異なり、**現在時刻を動的に生成できるため秒まで入る**。

| 入力 | 展開結果(既定) |
|------|------------------|
| `いま` | `18:28` |
| `いまs` | `18:28:07` |
| `きょう` | `2026/08/14(金)` |
| `にちじ` | `2026/08/14(金) 18:28` |

- 展開は打鍵直後に自動で行う
- **直後に1回だけ取り消せる**こと。「今日は暑い」と書きたいのに展開されては困るため、取り消し導線は必須
- **各キーワードの書式は「既定の書式に従う」を選べること**、かつそれを初期値とする。既定の書式を変えたのに展開キーワードだけ古い書式のまま残ると、設定が反映されていないように見えるため
- **展開キーワードは設定から自由に追加・変更・削除・全無効化できる**こと。`いま` `きょう` のような日常語を割り当てると通常の入力が奪われる場面があるため、これは任意機能ではなく必須要件とする
- 誤爆を避けたい利用者のために、記号ベースのキーワード(`;t` `;d` など)へ一括で切り替えるプリセットを用意する
- あるキーワードが別のキーワードの先頭部分と一致する場合(`いま` と `いまs` など)、短い方が先に展開されて長い方が使えなくなる。設定画面でこの旨を注意表示する

##### ③ 自動打刻

- 空行を挟んで新しい段落を書き始めたとき、その行頭に自動で打刻する
- 既定はオフ。設定でオンにする(常時オンだと通常の日記記述で邪魔になるため)
- オンのときも、その場で取り消せること

##### ④ キーボードショートカット(PC 向け)

- `F5` をエディタにフォーカスがあるときのみ打刻に割り当てる。設定でオフにできる
- ブラウザのリロードを完全に奪わないよう、`Ctrl/Cmd + R` は常に本来の動作を維持する
- 代替として `Ctrl/Cmd + ;` も割り当てる

#### 6.2.2 打刻の書式

- 既定書式: `HH:mm`(例 `18:28`)。1日1ページのため日付は通常不要
- 選択可能な書式: `HH:mm:ss` / `YYYY/MM/DD HH:mm` / `MM/DD(曜) HH:mm` / `[HH:mm]` / ISO 8601
- **すべての書式は正規表現で一意に解析できること**(§6.1 の設計判断による制約)
- 挿入位置は「カーソル位置」または「常に行頭」を設定で選べる
- 書式は設定で変更でき、過去の記述は書き換えない(記録の改変をしない)

### 6.3 保存【MVP】

- **自動保存**とする。保存ボタンによる明示的な操作を必須にしない
- 入力停止後すぐ(数百ミリ秒)に保存する。加えてページ離脱時・バックグラウンド化時にも保存する
- 「保存し忘れて消えた」は本プロダクトにおける**最も重大な欠陥**とみなす
- 保存済みであることが分かる控えめな表示を置く(利用者を不安にさせないため)

### 6.4 閲覧・検索【MVP】

- 日付一覧から過去のページを開ける。記述のある日が分かること
- 前日 / 翌日への移動が1タップでできる
- 全文検索。ヒットした日付と該当箇所の前後を表示する
- 過去のページも編集できる(後から追記・修正するため)

### 6.5 エクスポート / インポート【MVP・必須】

ブラウザ内保存のみという前提上、**データを人質にしない**ことは倫理的要件である。

- 全データを Markdown(日付ごとの見出し + 本文)で書き出せる
- 全データを JSON で書き出せる(構造を保った完全バックアップ)
- 書き出した JSON から復元できる
- バックアップ導線を設定画面の目立つ位置に置き、最終バックアップ日時を表示する

### 6.6 タイムライン表示【Phase 2】

- その日の本文を解析し、打刻を時系列に並べて表示する
- 各打刻の間隔(経過時間)を併記する。「何に何時間使ったか」が読み取れる
- 表示専用とし、ここから本文は編集しない(データの二重管理を避けるため)

## 7. データモデル

```jsonc
{
  "version": 1,
  "settings": {
    "stampFormat": "HH:mm",
    "insertPosition": "cursor",      // "cursor" | "lineStart"
    "autoStampOnNewParagraph": false,
    "textExpansions": { "いま": "HH:mm", "きょう": "YYYY/MM/DD(ddd)" },
    "enableF5": true
  },
  "entries": {
    "2026-08-14": {
      "date": "2026-08-14",
      "body": "09:12 出社。メールが溜まってる\n\n11:40 設計レビュー終了",
      "createdAt": "2026-08-14T09:12:03+09:00",
      "updatedAt": "2026-08-14T18:28:41+09:00"
    }
  },
  "lastBackupAt": "2026-08-10T22:00:00+09:00"
}
```

- 日付キーはローカルタイムの `YYYY-MM-DD`
- `createdAt` / `updatedAt` は利用者の操作なしに自動記録する
- 打刻の一覧は保持しない。§6.1 の通り `body` から解析して得る
- 保存先は当面 localStorage とするが、容量上限(概ね 5MB)に備え、**保存処理は差し替え可能な形に分離**し、将来 IndexedDB へ移行できるようにする

### 7.1 日付の境界

深夜に書く利用者を考慮し、**「1日の始まり」を設定可能**とする(既定 0 時、例えば 4 時に設定すれば深夜 2 時の記述は前日のページに入る)。日記アプリでは実利用上の影響が大きいため MVP に含める。

**日付が変わった直後の見え方を、データ消失と誤解させないこと。** 0 時を回ると今日のページは空で開くため、直前まで書いていた利用者にはこれが「保存されていない」と映る。実際に利用者から同じ報告を受けた。したがって以下を必須とする。

- 日付の横に**今日かどうかを示す**。空のページを見ているとき、それが別の日であると読み取れること
- 今日のページが空で、かつ**直近(18時間以内)に別の日へ書いていた場合**、その内容が残っている旨と、そこへ戻る手段を画面上に出す

## 9. 非機能要件

### 9.1 性能・可用性

| 項目 | 基準 |
|------|------|
| 起動 | 1秒以内に書き始められる |
| 打刻の応答 | 体感ゼロ(100ms 以内) |
| オフライン | 通信なしで全機能が動作する |
| 対応環境 | iOS Safari(主)、Android Chrome、PC の主要ブラウザ |

### 9.2 iOS Safari 固有の技術要件【最重要】

主要端末が iPhone であるため、以下は「あれば良い」ではなく**必須要件**とする。

1. **打刻ボタンをタップしてもエディタのフォーカスが外れないこと**
   タップ操作の既定動作を抑止してフォーカスを維持する。これができないとキーボードが閉じ、カーソル位置も失われ、打刻体験が完全に破綻する。
2. **打刻バーがキーボードの真上に追従すること**
   キーボード表示によって変化する表示領域を検出して追従させる。固定位置指定だけではキーボードの下に隠れる。
3. **画面の高さをキーボード表示に追従させること**
   従来の高さ指定は iOS Safari のアドレスバーで破綻するため、動的な単位を用いる。
4. **文字入力の変換中(日本語入力の未確定状態)に打刻や自動処理が割り込まないこと**
   変換確定前に文字列を書き換えると入力が壊れる。

### 9.3 プライバシー

- 日記の内容を外部に一切送信しない
- アクセス解析・外部フォント・外部スクリプトを読み込まない(自己完結した静的ファイルとする)
- この方針を利用者に明示する

### 9.4 データ保全

- 保存の失敗を検知し、利用者に伝える(黙って失敗しない)
- 保存容量の上限に近づいたら警告する
- 直前の状態への復帰手段を用意する(編集中の誤操作対策)

## 10. 受け入れ条件

MVP は以下がすべて満たされたときに完成とする。

1. iPhone の Safari で開き、**何も設定せずに文章を書いて打刻できる**
2. 打刻ボタンをタップしても**キーボードが閉じず、カーソル位置が保たれる**
3. 本文中に `いま` と打つと現在時刻に置換され、**その置換を取り消せる**
4. ブラウザを完全に閉じて開き直しても、書いた内容が失われていない
5. 過去の任意の日付を開いて追記できる
6. 全文検索で過去の記述を見つけられる
7. 全データを Markdown と JSON で書き出せ、JSON から復元できる
8. 通信を切断した状態でも 1〜7 がすべて動作する
9. 日本語入力の変換中に打刻しても入力中の文字列が壊れない

## 12. 意匠方針(決定済み)

**素のテキストエディタ、メモ帳そのものの見た目とする。**

- 装飾を持たない。太字・斜体・見出し・色分けなどの書式機能は**実装しない**(§5.4 の通りスコープ外)
- 書体は**端末の標準書体のみ**を使う。書体の選択機能は設けない。外部フォントは読み込まない(§9.3)
- 画面上の要素は「日付」「本文」「打刻バー」に絞り、それ以外の装飾要素を置かない
- 端末の明暗設定に追従する(暗所で書けることは実用上必要なため)
